# Skill: 需求管理 📥

> 版本：2.1 | 安全等级：🟢 无风险（纯文档管理）
> 定位：多需求排队与状态流转的持久层；单个需求的设计→计划→实现走 [brainstorming](../brainstorming/SKILL.md) → [writing-plans](../writing-plans/SKILL.md)。

## 触发条件

用户发送如下格式的消息时自动触发：

```
待开发：
任务1 描述
任务2 描述
任务3 描述
```

或关键词：`新需求` / `需求管理` / `需求清单`

## 执行流程

### Step 0：规格提取（Spec First）

> 参考 obra/superpowers：不急着动手，先搞清楚用户到底要什么

收到新需求后，**不要直接跳到实现**。先执行：

1. **追问意图**：用户说"加个功能"时，问清楚：
   - 解决什么问题？（场景）
   - 期望什么效果？（验收标准）
   - 有什么约束？（时间/技术/依赖）
2. **分块确认**：将规格拆成小块（每块 ≤ 5 行），逐块让用户确认
3. **记录原始描述 + 确认后的规格**到需求文档

**跳过条件**：用户已提供足够详细的需求描述时可直接进入 Step 1。

### Step 1：创建计划目录

- 获取当前日期 `YYYY-MM-DD`
- 创建目录 `plans/{date}_{主题}/`

### Step 1.1：更新 `plans/task-queue.md`（唯一状态文件）

新计划按三区管理：

1. **有进行中任务** → 新计划追加到"📋 排队中"表格末尾
2. **无进行中任务** → 新计划直接写入"🟢 进行中"区域
3. **永远不要删除历史**，已完成任务移到"✅ 已完成"区域

**顺位规则**：
- 任务完成 → 从"进行中"移到"已完成" → 排队中第一个自动上位到"进行中"
- 任务暂缓 → 移回"排队中"末尾

### Step 1.5：创建 plan.md 总览

在计划目录下创建 `plan.md`，作为新会话的上下文入口：

```markdown
# {日期}_{主题}

## 进度概览
| # | 需求 | 优先级 | 状态 |
|---|------|--------|------|
| 01 | ... | P0 | ⏳ 待开发 |

## 关键决策
（讨论过程中记录的关键技术/产品决策）

## 上次会话终点
（每次会话结束时更新，告诉下一个会话从哪里继续）

## 相关文件
（需求文档、设计文档、落地评估等路径）
```

新会话开头：读 `plans/task-queue.md` 获取"进行中"任务的计划目录 → 读 `plan.md` 获取完整上下文。

### Step 2：设计文档 + 子计划

复杂需求可能需要额外的设计文档（如集成方案、架构设计）：

- 文件命名：`plan-{主题}-integration.md`、`plan-{主题}-design.md`
- 放置在计划目录下，与 `plan.md` 并列
- `plan.md` 的"相关文件"章节链接到这些子文档

示例结构：
```
plans/2026-04-20_{主题}/
├── plan.md                    ← 总览入口
├── plan-{主题}-design.md      ← 子计划：设计
└── report-xxx.md              ← 可选：报告/评估
```

### Step 2.5：任务分解

> 参考 obra/superpowers：实现计划要清晰到"热情但缺乏判断力的初级工程师也能跟进"

在 `plan.md` 中将需求分解为**可独立执行的任务清单**：

```markdown
## 任务清单

| # | 任务 | 验收标准 | 预估 | 状态 |
|---|------|----------|------|------|
| T1 | 创建 xxx 模块 | 模块可 import，测试通过 | 30min | ⏳ |
| T2 | 集成 xxx API | 端到端测试通过 | 1h | ⏳ |
```

**分解纪律（YAGNI + DRY）**：
- **YAGNI**：只分解当前确认需要的功能，不为"以后可能用到"预建架构
- **DRY**：复用已有模块，不重复造轮子
- **每个任务有明确验收标准**：不说"做好了"，要说"xxx 测试通过"或"xxx 命令返回预期结果"
- **任务粒度**：每个任务 ≤ 2h 可完成；超过则继续拆分

### Step 3：为每个需求创建文档

文件名约定（状态前缀排序，天然按生命周期排布）：
- `_01_需求简称.md` — 待讨论
- `_wip_02_需求简称.md` — 开发中
- `_done_03_需求简称.md` — 已完成
- `_hold_04_需求简称.md` — 暂缓

### Step 4：需求文档模板

```markdown
# 需求：{标题}

## 原始描述
（用户原话，不丢失意图）

## 资深工程师建议
（技术可行性、架构建议、风险点、依赖）

## 忠实用户补充
（使用场景、体验期望、边界条件）

## 维护者落地计划
（分步方案、估时、优先级、依赖关系）

## 决策记录
| 时间 | 决策 | 理由 |
|------|------|------|

## 当前状态
⏳ 需求收集中 / 🟡 讨论中 / 🔧 开发中 / ✅ 已完成 / 🔒 暂缓
```

### Step 5：执行循环（Task → Review → Continue）

> 参考 obra/superpowers 的 subagent-driven development：自主推进 + 逐任务验证

开发过程中按任务清单执行：

1. **执行任务**：从 T1 开始，按顺序逐个完成
2. **即时验证**：每个任务完成后立即验证验收标准（运行测试/命令检查）
3. **记录结果**：更新 `plan.md` 任务状态
4. **遇到阻塞**：
   - 可解决的 → 解决并继续
   - 需要用户决策的 → 暂停并提问，记录到"决策记录"
5. **自主推进**：可连续完成多个任务无需确认，直到：
   - 所有任务完成
   - 遇到需要用户决策的问题
   - 会话即将结束（→ Step 6 遗留处理）

### Step 6：遗留事项处理

会话结束时有未完成项：

1. 在 `plan.md` 的进度表中更新已完成项状态
2. 在 `plan.md` 的"上次会话终点"章节写入：
   - 本次完成了什么
   - 下次从哪里继续（具体到任务编号）
   - 关键上下文（避免下次会话丢失）
3. 如有新发现的待开发项，创建对应需求文档

### Step 7：归档规则

#### 单个需求状态变更

- 单个需求完成：rename 文件加 `_done_` 前缀
- 单个需求暂缓：rename 文件加 `_hold_` 前缀

#### 批量归档流程

当计划目录下所有需求已完成/暂缓：

1. **扫描** — 列出 `plans/` 下所有 `YYYY-MM-DD_` 前缀目录
2. **判断** — 读取 `plan.md` 状态标记（`✅ 已完成` / `❌ 已废弃`）
3. **移动** — `mv plans/{目录} plans/archive/`
4. **关联文档检查** — 归档后检查关联清单是否需更新（服务清单/技能索引等，如维护；`task-queue.md`：如归档的是当前任务，更新进行中→已完成，下一个排队任务自动上位）
5. **输出摘要** — 归档了哪些 + 保留了哪些

### Step 8：远程入口兼容

文档结构标准化后，任何远程入口（Bot 命令 / CLI / 另一台机器的 agent）都按三级定位上下文：

1. 读 `plans/task-queue.md` 获取"进行中"任务的计划目录
2. 列出目录下所有需求文档
3. 读取对应文档获取完整上下文

## 注意事项

- 原始描述必须保留用户原话，不加工不丢失
- 决策记录必须带时间戳（含时刻，如 `04-15 10:30`）
- 文档是活的，讨论过程中持续更新
- 优先级排序遵循：P0 安全 > P0 功能 > P1 > P2
- **YAGNI**：不为未来需求预建架构，只做当前确认需要的
- **DRY**：复用已有模块，发现重复时先提取公共部分
- **验收驱动**：每个任务都有明确的"做完了"的标准，不说"大概好了"

## 验证

- [ ] 新需求已过规格确认（或满足跳过条件）；原始描述逐字保留
- [ ] task-queue 三区状态与实际一致；顺位规则未被破坏（无删历史）
- [ ] plan.md 含进度概览/关键决策/上次会话终点；任务都有验收标准
- [ ] 归档走了完整流程（含关联文档检查与输出摘要）

**On failure:** 状态漂移 → 对照实际文件重对齐 task-queue；缺验收标准的任务 → 回 Step 2.5 补分解。
