# Skill: 提问智慧 🧠

> 版本：3.3 | 安全等级：🟢 无风险（纯思维框架，无网络/文件操作）

---

## 目标

<HARD-GATE>
在完成需求追问清单并获得用户明确确认前，**绝不**执行任何实现动作（不写代码、不建项目、不改配置）。
</HARD-GATE>

### 术语定名与歧义守门（v3.3）

- **定名**：本技能做的是「**优化需求陈述**」——把用户的表达变得更精准、完整、无歧义；**绝不改变、增删、歪曲需求本身**。用户常简说「优化需求」甚至「优化」，指的仍是这件事。
- **歧义守门**：用户使用「优化」类短指令（优化 / 优化需求 / 优化一下 / 改一下）时，可能指多种对象——优化需求陈述 / 优化系统 / 优化代码 / 优化提示词。**上下文无法唯一判定时，列出候选理解请用户选择，禁止默认揣测为其中任何一个**（`[NEEDS CLARIFICATION]` 标记纪律的触发词特例）。澄清一句话，返工一整轮。
- **语义边界**：本技能管需求输入侧（需求进来前澄清）；推理过程侧的质量归 CoT 质量禁令（本仓 [snippets/AGENTS-cot.md](../../snippets/AGENTS-cot.md)）——两道不同的闸门。

将提问哲学转化为 AI 协作场景的思维框架，实现五层价值：

1. **需求诊断** — 模糊需求 → 精准追问清单 → 输出给用户确认
2. **思维自检** — agent 执行任务前的内部检查（先想清楚再动手）
3. **Grilling Session** — 主动式强制对齐，适用于复杂任务
4. **共享语言** — CONTEXT.md 减少 agent 上下文消耗
5. **小模型注入** — 精炼版作为种子经验，提升小参数量模型自主分析质量

## 核心原则（ESR 六律）

| # | 律 | 一句话 | AI 协作转化 |
|---|-----|--------|------------|
| 1 | 目标先于路径 | 描述目标，而非步骤 | 用户说「怎么把 A 变成 B」→ 先问「你想达成什么效果」 |
| 2 | 症状先于猜测 | 描述症状，而非猜测 | 用户说「应该是 XX 导致的」→ 先问「你观察到了什么现象」 |
| 3 | 精确先于冗长 | 量不是精确 | 用户贴 500 行日志 → 先问「哪 20 行是核心」 |
| 4 | 显式先于隐式 | 对问题要明确 | 用户说「帮我看看这个」→ 先问「你希望我关注什么方面」 |
| 5 | 功课先于求助 | 先搜索先实验 | 用户问「XX 怎么做」→ 先问「你查过什么」 |
| 6 | 闭环先于遗忘 | 跟进解决方案 | 任务完成后记录决策和踩坑到记忆系统 |

> 各律的追问模板和自检清单 → 见 `<supporting-info id="esr-details">`

## 模式体系

### 🔍 模式 A：需求诊断（默认模式）

**触发**：需求描述 < 30 字 / 缺少成功标准 / 只有路径没有目标

**流程**：
1. 识别需求中的模糊点（目标？症状？范围？约束？已有尝试？）
2. 生成 3-5 个精准追问（不要变成审讯）
3. 给出初步理解 + 建议执行方向
4. 等待用户确认

**输出格式**：

```markdown
## 🧠 需求诊断
> 原始需求：「{用户原话}」

### 需要澄清的问题
| # | 类别 | 问题 | 为什么问 |
|---|------|------|---------|

### [NEEDS CLARIFICATION] 标记
（所有不确定处必须显式标记，不允许用"假设"跳过）
> [NEEDS CLARIFICATION: 具体问题] — 任何模糊、歧义、多种理解之处

### 我的初步理解
（基于已有信息的最佳猜测，**仅限已确认部分**）

### 建议的执行方向
（如果理解正确，建议的落地方式。**标记了 [NEEDS CLARIFICATION] 的部分不进入执行方向**）
```

**注意**：需求已明确时直接执行，不过度诊断。

### 🪞 模式 B：思维自检（内部模式）

**触发**：agent 开始执行任何非平凡任务前自动触发（不对外输出，在 thinking 中完成）

```
🧠 思维自检（3 秒）
├─ 目标：我理解的是目标还是路径？
├─ 症状：我在分析事实还是推测？
├─ 精确：我能缩小问题范围吗？
├─ 显式：交付物和成功标准明确吗？
├─ 功课：我查过现有文档/记忆了吗？
└─ 闭环：结束后需要记录什么？
```

任一不通过 → 触发模式 A 向用户追问，或自行探索后再执行。

### 🔥 模式 D：Grilling Session（强制对齐）

**触发**：多文件改动(>3) / 架构决策 / 破坏性变更 / 首次请求此类任务 / 用户说"grill"/"对齐"

**流程**（总问题 ≤ 6 个）：

```
Step 1: 目标确认 — "你要达成什么效果？"
Step 2: 范围界定 — "影响哪些模块？有不想改的部分？"
Step 3: 约束提取 — "技术约束？时间约束？"
Step 4: 成功标准 — "怎样算做完了？"
Step 5: 输出对齐摘要（维度 + 确认内容 + 确定性标记）
```

**输出格式**：

```markdown
## 🔥 Grilling Session 摘要
> 触发原因：{为什么需要对齐}

| 维度 | 确认内容 | 确定性 |
|------|---------|--------|
| 目标 | ... | ✅ 确定 / ⚠️ 假设 |
| 范围 | ... | ✅ 确定 / ⚠️ 假设 |
| 约束 | ... | ✅ 确定 / ⚠️ 假设 |
| 成功标准 | ... | ✅ 确定 / ⚠️ 假设 |

⚠️ 标记为「假设」的维度需要你确认，我才会动手。
```

### 📤 模式 E：共享语言注入

**触发**：Agent 首次进入项目 / 用户提到"共享语言"/"术语表" / 收工流程的一部分

读取 `CONTEXT.md`（项目共享术语表），注入上下文。维护方式：收工或阶段性整理时同步更新。

> 共享语言的具体术语表 → 见 `<supporting-info id="shared-language">`

### 📤 模式 C：小模型注入（导出模式）

将精炼版思维框架注入小参数量模型的 system prompt。

## 模式选择指南

| 场景 | 模式 | 原因 |
|------|------|------|
| 用户提了模糊需求 | A 需求诊断 | 被动响应，3-5 个问题 |
| 复杂任务（多文件/架构） | D Grilling Session | 主动对齐，结构化 |
| Agent 进入新项目 | E 共享语言 | 减少术语理解成本 |
| 为小模型提升思维质量 | C 小模型注入 | 精炼版注入 |
| Agent 开始执行前 | B 思维自检 | 内部检查，不输出 |
| 用户说"grill"/"对齐" | D Grilling Session | 显式触发 |

## 约束

### 必须做
- 保留用户原话，不加工不丢失
- 模式 A 追问数量控制在 3-5 个
- 模式 D 问题总数不超过 6 个
- 需求已明确时直接执行，不过度诊断
- 模式 B 在 thinking 中完成，不输出给用户
- **[NEEDS CLARIFICATION] 强制标记**：所有输出中的不确定处必须标记 `[NEEDS CLARIFICATION: 具体问题]`，不允许用"假设"跳过。下游技能（brainstorming、writing-plans）在门禁检查时会验证此标记是否已解决

### 不要做
- ❌ 不要把诊断变成审讯
- ❌ 不要替用户做决策（列出选项让用户选）
- ❌ 不要在简单任务上过度应用（改个 typo 不需要思维自检）
- ❌ 不要忽略用户已有的思考痕迹
- ❌ 不要在模式 D 中重复问模式 A 已确认的信息

## ESR 六律详细指南

### 律 1：目标先于路径（Goal Before Step）

> ESR 原文：「描述目标，而非步骤」
> mattpocock：/grill-me 首先确认「what does success look like?」

**AI 协作转化**：用户说「怎么把 A 变成 B」时，先问「你想达成什么效果」。因为用户选定的路径可能是错的，更好的方案可能存在。

**追问模板**：
- 你最终想实现的效果是什么？（不是「怎么做」，是「做成什么样」）
- 这个需求背后的业务场景是？
- 有没有可能用完全不同的方式达成同样目的？

**自检清单**：
- [ ] 我理解的是用户的**目标**还是用户**以为的路径**？
- [ ] 有没有更简单的方案能达到同样效果？

### 律 2：症状先于猜测（Symptoms Before Guesses）

> ESR 原文：「描述问题的症状，而非你的猜测」「所有诊断师都来自密苏里——Show Me」

**AI 协作转化**：用户说「应该是 XX 导致的」时，先问「你观察到了什么现象」。不要被用户的诊断带偏。

**追问模板**：
- 你看到的具体现象是什么？（错误信息、异常行为、预期 vs 实际）
- 这个问题在什么条件下出现？什么条件下不出现？
- 能提供复现步骤吗？

**自检清单**：
- [ ] 我在分析的是**可观测的事实**还是**用户的推测**？
- [ ] 我是否先验证了用户的假设，还是直接接受了？

### 律 3：精确先于冗长（Precision Before Volume）

> ESR 原文：「量不是精确」「提供最小复现用例」

**AI 协作转化**：用户贴了 500 行日志时，先问「哪一段是关键」。上下文窗口是稀缺资源。

**追问模板**：
- 能缩小问题范围吗？最小复现是什么？
- 这 500 行里，哪 20 行是核心？
- 去掉哪些部分后问题仍然存在？

**自检清单**：
- [ ] 我是否在处理**信号**还是被**噪声**淹没？
- [ ] 我能否把问题缩减到最小可复现的形式？

### 律 4：显式先于隐式（Explicit Before Implicit）

> ESR 原文：「对你的问题要明确」「开放式问题 = 开放式时间黑洞」

**AI 协作转化**：用户说「帮我看看这个」时，先问「你希望我关注什么方面」。

**追问模板**：
- 你希望我做什么？（审查 / 修复 / 重构 / 解释 / 对比）
- 成功标准是什么？（怎样算完成了？）
- 有什么约束条件？（性能、兼容性、时间、技术栈）

**自检清单**：
- [ ] 我知道**具体的交付物**是什么吗？
- [ ] 我知道**怎样算完成**吗？
- [ ] 我是否在处理一个**有边界**的任务？

### 律 5：功课先于求助（Homework Before Help）

> ESR 原文：「先搜索、先读文档、先实验」「展示你做过什么，而非一无所知」

**AI 协作转化**：用户问「XX 怎么做」时，先问「你查过什么」。这不仅是效率问题，更是用户是否思考过的信号。

**追问模板**：
- 你已经尝试过什么？（搜索过什么、看过什么文档、试过什么方法）
- 你查到的信息里，哪部分不理解？
- 有没有相关的错误信息或日志？

**自检清单**：
- [ ] 我是否先检查了现有文档/记忆/索引？
- [ ] 用户是否展示过思考痕迹？（有 → 认真对待；无 → 先引导）

### 律 6：闭环先于遗忘（Closure Before Forgetting）

> ESR 原文：「用简短说明跟进解决方案」「这比常规礼貌更重要」

**AI 协作转化**：任务完成后，记录决策、踩坑、方案到记忆系统。

**自检清单**：
- [ ] 关键决策记录了吗？
- [ ] 踩坑经验写入记忆系统了吗？
- [ ] 方案可复现吗？

## 验证

> 全部通过才算完成（可检验的结果，不是"原则性符合"）。

- [ ] 追问清单已输出，每条带「为什么问」；不确定处全部带 `[NEEDS CLARIFICATION]` 标记，无静默假设
- [ ] 用户原话逐字保留在诊断输出中
- [ ] 用户已明确确认理解（模式 A 或 D 至少其一走完）；确认前无任何实现动作（HARD-GATE 未破）
- [ ] 「优化」类短指令若存在歧义，候选理解清单已列出并交用户选择

**On failure:** 回到追问阶段重新对齐，不进入执行。
