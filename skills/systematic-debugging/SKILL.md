# Skill: 系统调试 🐛

> 版本：1.2 | 安全等级：🟡 中风险（会修改代码，需要谨慎）
> 灵感来源：obra/superpowers — systematic-debugging skill + DietrichGebert/ponytail root-cause rule
> 互补技能：[brainstorming](../brainstorming/SKILL.md)（新功能设计）；代码质量提升是独立流程，不在本技能内

---

## 目标

用结构化的 4 阶段流程系统化地定位和修复 bug，避免凭直觉猜测、盲目打印日志、跳过根因直接打补丁。

<HARD-GATE>
在确认根因之前，**绝不**修改任何代码。修改代码只在阶段4（修复验证）中进行。
</HARD-GATE>

---

## 反模式

| 反模式 | 表现 | 危害 |
|--------|------|------|
| **猜测驱动调试** | "我觉得是这个问题" → 直接改代码 | 改错地方，引入新 bug |
| **打地鼠** | 修了一个症状，又冒出另一个 | 根因未除，反复发作 |
| **随机打印** | 到处加 print/log | 信息淹没，方向迷失 |
| **跳过复现** | "我猜是这个问题" | 修了一个不存在的 bug |
| **补丁思维** | try-catch 吞异常、if 拦截 | 掩盖问题，制造技术债 |

## 4 阶段流程

### 阶段 1：复现（Reproduce）

<HARD-GATE>
不能复现的 bug 不能修。如果你无法复现，不要猜测根因。
</HARD-GATE>

- [ ] **1.1 获取完整错误信息** — 错误消息、堆栈跟踪、错误码、异常类型
- [ ] **1.2 确认复现条件** — 什么输入/状态/环境会触发？
- [ ] **1.3 最小化复现** — 找到最简单的触发方式
- [ ] **1.4 写复现测试** — 将复现步骤转为自动化测试

**复现检查清单**：
- 错误是确定性的还是间歇性的？
- 是否有特定的输入模式触发？
- 是否与环境（OS/版本/配置）相关？
- 是否与时序/并发相关？

### 阶段 2：隔离（Isolate）

- [ ] **2.1 二分法缩小范围** — 注释掉一半代码，看错误是否还在
- [ ] **2.2 检查变更历史** — `git log --oneline -20` + `git diff` 找到引入问题的提交
- [ ] **2.3 隔离变量** — 一次只改一个变量，观察影响
- [ ] **2.4 确认影响范围** — 哪些模块/功能受影响

**隔离技术**：
- **二分注释**：注释掉一半可疑代码 → 错误消失 → 问题在被注释的部分；错误仍在 → 问题在未注释的部分
- **Git Bisect**：`git bisect start` → 标记好/坏提交 → 自动定位引入问题的提交
- **依赖排除**：逐个排除外部依赖，看问题是否消失
- **环境对比**：在已知正常的环境 vs 当前环境间找差异

### 阶段 3：根因分析（Root Cause）

<HARD-GATE>
你必须能写出一句话的根因陈述。如果不能，你还没找到根因。
</HARD-GATE>

- [ ] **3.1 构建因果链** — 从症状反推，每一步都要有证据
- [ ] **3.2 区分根因 vs 症状** — 根因是"为什么发生"，症状是"发生了什么"
- [ ] **3.3 写一句话根因陈述** — "因为 X，导致 Y，表现为 Z"
- [ ] **3.4 验证根因假设** — 针对根因做最小修改，确认能修复

**根因陈述模板**：
```
根因：<具体的技术原因>
  因为：<底层原因/设计缺陷/假设错误>
  导致：<直接的技术后果>
  表现为：<用户可见的症状>

示例：
根因：process_message() 未处理 None 返回值
  因为：api_client.get() 在网络超时时返回 None 而非抛异常
  导致：后续 code.lower() 调用 AttributeError
  表现为：用户发送消息后程序崩溃
```

**根因追踪技术**：
- **5 Whys**：连续问5次"为什么"
- **追溯日志**：沿调用链反向追踪
- **状态快照**：在关键节点打印完整状态
- **条件断点**：在特定条件触发时暂停

### 阶段 4：修复验证（Fix & Verify）

- [ ] **4.1 设计最小修复** — 只改根因需要的，不顺便"改进"
- [ ] **4.2 写回归测试** — 先写测试验证 bug 存在，再修复
- [ ] **4.3 实施修复** — 最小改动
- [ ] **4.4 验证修复** — 运行回归测试 + 原有测试
- [ ] **4.5 检查副作用** — 修复是否引入新问题
- [ ] **4.6 提交** — 包含根因说明的 commit message

**修复原则**：
- **最小改动**：只改必须改的
- **修根不修叶**：修复根因而非屏蔽症状
- **不顺便重构**：修复就是修复，重构另外做
- **防御性编程**：修复后加防御措施，防止同类问题
- **🐴 Ponytail 规则 — 修共享函数，不修调用者**：bug 报告命名一个症状。修改前用 Grep 找出你将要修改的函数的所有调用者。在共享函数里加一个守卫（一个 if/一个断言），比在每个调用者加守卫的 diff 小——而且只修 ticket 指明的路径，其他兄弟调用者仍然坏着。懒的修复就是正确的修复：一次修好，所有调用者流过同一处。

**Commit Message 格式**：
```
fix: <一句话描述修复了什么>

根因：<根因陈述>
修复：<具体做了什么>
测试：<添加了什么回归测试>
```

## Defense in Depth（纵深防御）

修复完成后，检查是否需要加防御层：

| 防御层 | 适用场景 | 示例 |
|--------|---------|------|
| **输入验证** | 外部输入导致问题 | 参数校验、类型检查 |
| **不变量断言** | 内部状态被破坏 | assert 条件 |
| **错误处理** | 异常未处理 | try-catch + 有意义的错误消息 |
| **日志/监控** | 问题难以复现 | 关键路径加日志 |
| **类型系统** | 类型混淆 | 类型注解 + mypy |

## Condition-Based Waiting（条件等待）

处理时序/异步/竞态相关问题时：

```python
# ❌ 错误：固定等待
time.sleep(5)  # "等一会就好了"

# ✅ 正确：条件等待
import time
def wait_for_condition(check_fn, timeout=30, interval=1):
    """等待条件满足，超时抛异常"""
    start = time.time()
    while time.time() - start < timeout:
        if check_fn():
            return True
        time.sleep(interval)
    raise TimeoutError(f"条件等待超时: {timeout}s")
```

**原则**：
- 永远不用固定 `sleep` 解决时序问题
- 用条件轮询或事件通知
- 必须有超时机制

## 常见调试场景速查

| 场景 | 首选策略 |
|------|---------|
| 间歇性崩溃 | 加日志 → 捕获完整状态 → 复现 |
| 性能退化 | git bisect + 性能基准对比 |
| 并发 bug | 检查共享状态 + 锁顺序 + 竞态条件 |
| 第三方库报错 | 读源码 → 最小复现 → 升级/绕过 |
| 配置相关 | 对比正常/异常环境差异 |
| 数据相关 | 检查边界值 + 空值 + 类型 |

## 约束

### 必须做
- 严格按4阶段顺序执行
- 每个阶段有明确的完成标准
- 修复后必须添加回归测试
- Commit message 包含根因说明
- 值得沉淀的踩坑，修复后记录进你的记忆/踩坑记录系统

### 不要做
- ❌ 阶段3之前修改代码
- ❌ 用 try-catch 吞掉异常作为"修复"
- ❌ 在未理解根因时添加 sleep/retry
- ❌ 一次修多个不相关的 bug
- ❌ 修复后不运行测试

---

## 与其他技能的关系

- **brainstorming**：如果 bug 涉及架构问题 → 修复后可能需要重新设计
- **记忆/踩坑系统**：调试中的踩坑经验 → 修复后写回，避免重蹈
- **边界**：调试只修 bug，不顺手重构、不做质量提升——那是独立的清洗流程

## 反借口表（Anti-Rationalization）

> 以下表格预判 agent 在调试过程中可能找的借口，并给出预设反驳。

| 你正在想… | 实际情况 |
|-----------|---------|
| "我知道 bug 在哪，不需要复现" | **没有复现 = 不能验证修复。** 每一个没有复现的修复都是猜测。 |
| "先试试这个修复，不行再说" | **一次只改一个变量。** 同时改多个变量，你根本不知道哪个有用。 |
| "测试通过了，bug 修好了" | 测试只覆盖了你想到的 case。没想到的 case 呢？ |
| "加个 try-catch 包一下就好了" | **吞异常不是修复。** 异常是被掩盖的症状，根因还在。 |
| "这个 bug 太简单了，不用走流程" | 简单的表象下可能隐藏复杂的根因。走流程不花多少时间。 |
| "加个 sleep 应该能解决" | **固定等待永远不是解决方案。** 用条件等待代替。 |
| "这是第三方库的 bug" | 在归咎框架之前，先在你自己代码里复现它。 |
| "先把补丁打上，后续再找根因" | "后续"永远不会来。补丁打了就没人再关心根因了。 |

## Red Flags

| 你在想… | 实际情况 |
|---------|---------|
| "我猜是这个问题" | 猜测不是调试，是赌博 |
| "加个 try-catch 就好了" | 吞异常不是修复 |
| "先改改看" | 改之前必须理解根因 |
| "这个问题太简单了" | 简单的表象下可能隐藏复杂的根因 |
| "加个 sleep 应该能解决" | 固定等待永远不是解决方案 |
| "重启一下试试" | 不能复现 = 不能修复 |
| "这是框架的bug" | 在归咎框架之前，先确认你的代码 |

## 验证

> 全部通过才算完成（可检验的结果，不是"原则性符合"）。

- [ ] 四阶段按序完成；修复前已有一句话根因陈述与复现测试（阶段 1/3 门禁未破）
- [ ] 回归测试通过，且原有测试无回归
- [ ] commit message 含根因说明；无「顺便重构」类超范围改动
- [ ] 值得沉淀的踩坑已写回记忆系统（若有）

**On failure:** 回到根因分析阶段重新执行，不带悬案收尾。
