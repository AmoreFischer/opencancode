# 工程原则检查清单

> 对照本仓 [rules/iron-rules.md](../../../rules/iron-rules.md)（唯一权威源），每次清洗时逐项检查
> 此文件可被自动追加新检查项（模式结晶机制）

---

## #3 — 完整生命周期 + 验证门禁
- [ ] 所有数据库连接使用 with 上下文管理器
- [ ] 所有文件操作使用 with open()
- [ ] httpx 客户端使用 async with
- [ ] 无无上限缓存/队列
- [ ] 进程/线程有明确的创建和终止路径

## #4 — 单一职责
- [ ] 无超过 50 行的函数
- [ ] 无上帝文件（混合 3+ 职责的模块）
- [ ] 每个模块只做一件事
- [ ] 上帝文件判定已做**内容密度评估**：模板/配置/卡片类文件行数多≠要拆，先看密度再看行数（实例：5 个 322~1220 行的模板/配置类文件经密度评估均判不拆）

## #5 — 防御式编程
- [ ] 所有外部输入（API 响应、用户消息、文件内容）有类型校验
- [ ] 边界条件已处理（空值、零值、超大值）
- [ ] 无硬编码密钥/凭据
- [ ] 无硬编码魔数（超时值、阈值等应提取为命名常量）

## #6 — DRY
- [ ] 无重复代码片段（≥3 行相似）
- [ ] 无重复常量定义
- [ ] 公共逻辑已抽取为函数/常量

## #7 — KISS
- [ ] 无过度抽象（不必要的中间层）
- [ ] 无不必要的复杂条件嵌套
- [ ] 能 3 行解决的没有写 30 行

## #8 — 失败可观测性
- [ ] 无静默吞异常（bare except: pass）
- [ ] 异常带上下文日志（logger.error 带 exc_info）
- [ ] 关键路径有 logger.info

## #9 — 向后兼容
- [ ] 破坏性变更已升主版号
- [ ] API 接口变更向后兼容

## #10 — 避免过早优化
- [ ] 无不必要的缓存（没有 profiler 数据不缓存）
- [ ] 无不必要的并发

## #11 — 代码即文档
- [ ] 变量名/函数名自描述
- [ ] 注释只写"为什么"，不写"做什么"
- [ ] 函数有类型注解
- [ ] 模块有 docstring

## #16 — 依赖纪律
- [ ] 依赖版本已锁定
- [ ] 无不必要的第三方依赖
- [ ] 能用标准库就不用第三方

## #12-#15 — Karpathy 编码准则（PR 评审）

> 来源：Karpathy 编码准则（rules/iron-rules.md #12-#15，溯源见 SOURCES.md）

- [ ] 每一行修改都能追溯到用户请求？（精确修改）
- [ ] 没有添加未被要求的功能或抽象？（简单优先）
- [ ] 不确定的地方有提出来而不是悄悄假设？（先想清楚）
- [ ] 有明确的成功标准且已验证通过？（目标驱动）
- [ ] 50 行能解决的没写成 200 行？（KISS）
- [ ] 没有顺手重构没坏的东西？（精确手术）

## 诊断性问题 R1-R6（四段式产出）

> 吸收自 [hyhmrright/brooks-lint](https://github.com/hyhmrright/brooks-lint)（MIT，方法论吸收不复制文本）——12 本经典软件工程书蒸馏
> 用法：上方勾选项答"是/否"；本组诊断问题产出**发现**——设计问题不能只打勾。
> 发现格式：`🔴/🟡/🟢 [维度] 症状一句话` → 出处（铁律 #N）→ 后果 → 补救。严重度约定：🔴 必须修 / 🟡 应修 / 🟢 建议。

### R1 · 认知过载 — 理解这段代码要多少心智负担？

- **症状**：函数超 50 行、模块混合 3+ 职责、命名不表达意图、深层嵌套
- **出处**：铁律 #4（单一职责）、#11（代码即文档）
- **后果**：改动时无法局部推理，每次都要全文重读；接手成本高
- **补救**：按职责拆分；命名对齐意图；注释只写"为什么"

### R2 · 变更传播 — 改这一处会破坏多少不相干的东西？

- **症状**：一个类/方法因多个无关原因被改（Divergent Change）、牵一发动全身
- **出处**：铁律 #4（单一职责）、#14（精确修改）
- **后果**：每次编辑都带回归风险，bug 出现在远离改动点的地方
- **补救**：隔离变化轴——每个类只保留一个被改的理由；拆分耦合职责

### R3 · 知识重复 — 同一个决策是否在多个地方各自表达？

- **症状**：≥3 行相似代码块、重复常量、同一规则在代码/文档/配置中重复定义
- **出处**：铁律 #6（DRY）
- **后果**：改一处漏一处，行为漂移；规则多源=无权威源
- **补救**：抽函数/常量；规则只留权威源（引用而非复制）

### R4 · 偶发复杂度 — 代码是不是比问题本身更复杂？

- **症状**：为"以后"预留的抽象/配置、单实现接口、手写标准库已有能力、3 行写成 30 行
- **出处**：铁律 #7（KISS）、#10（避免过早优化）、#13（简单优先）
- **后果**：维护成本随代码量上涨；无 profiler 数据的"优化"反而害性能
- **补救**：YAGNI 删除；换标准库/平台原生；能短不写长

### R5 · 依赖失序 — 依赖方向是否一致、可替换？

- **症状**：循环依赖、底层依赖上层、版本未锁定、新依赖未经评估
- **出处**：铁律 #16（依赖纪律）
- **后果**：模块无法独立测试/替换；供应链风险；升级连锁反应
- **补救**：依赖单向流动（高层→低层）；锁版本；能用标准库不引第三方

### R6 · 领域模型扭曲 — 代码是否忠实表达领域规则？

- **症状**：业务规则散落/被绕过、魔数代替规则、关键逻辑无测试、边界条件未处理
- **出处**：铁律 #5（防御式编程）、#17（关键逻辑测试覆盖）
- **后果**：静默数据错误——系统看着正常但违反业务规则
- **补救**：规则显式建模+边界校验；关键逻辑补测试；魔数提取命名常量

## 动态追加区（模式结晶自动填充）

> 以下检查项由清洗过程中的模式结晶机制自动追加
> 格式：`- [ ] 检查项 — 结晶自 {来源}，出现 {N} 次`

- [ ] 模块拆分后验证：所有测试的 mock patch 路径指向新模块位置（非旧路径） — 结晶自拆分实践，出现 3+ 次
- [ ] 模块拆分后验证：被测方法/属性仍存在于目标类（若已删除/重命名则同步移除对应测试） — 结晶自拆分实践，出现 3+ 次
- [ ] mock 路径原则：patch 应指向函数**被使用**的位置（import site），而非定义位置 — 结晶自拆分实践，出现 3+ 次
