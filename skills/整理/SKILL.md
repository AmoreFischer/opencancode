# Skill: 整理 🧹

> 轻量级 · 日常会话卫生管家。会话级高频操作，无破坏性；重型全系统操作（大扫除/全量/月度盘点）**不在本技能范围**。
> 溯源：由历史版本的质量清洗技能重置拆分而来（轻量/系统级两分法）。

<HARD-GATE>
1. 本技能**只做无破坏性操作**——发现需要归档/删除/全库扫描等重型动作时，停下来提示用户转重型清理流程，不在此执行。
2. 局外人审视（L1.2）**只建议不执行**，拍板权在用户。
</HARD-GATE>

## L1: 阶段整理（工作中途，~8min）

> 定位：用户觉得已进行相当工作量、准备记录当前状态时触发。检查点固化 + 局外人建议**就地输出**（会话继续，当场可采纳）。

### L1.1 检查点落盘（~2min）

journal 当日文件追加「阶段检查点」段：本段弧线（做了什么）/ 系统态（关键状态）/ 在途待办。

### L1.2 局外人审视（~5min）

以**第一次接触本工作区的第三方评审者**视角回答三问：

1. **这串工作在解决什么问题**——从产出物反推用户当前目标与优先级（依据是做了什么，不是说过什么）
2. **盲区与更优路径**——没问过的问题、没考虑的替代方案、明显可复用却重造的轮子
3. **外部对照**——生态内有无现成方案/对标实践（先搜后造：只列线索不展开调研）

产出 3-5 条建议，**就地输出给用户**（用户可当场拍板采纳，直接影响下一段工作）；高价值项入任务队列「排队中」。确无可提时写「本段无可提」，不为凑数硬编。

### L1.3 状态刷新（~1min）

todo / 计划进度勾选；上下文压力大时提示用户（衔接 [极简沟通](../极简沟通/SKILL.md) 自动触发）。不写 CHANGELOG / handoff、不强制提交（那是 L2 收工的事）。

## L2: 收工（会话结束全套，L2.1-L2.9）

### L2.1 收集变更

```bash
git diff --stat && git diff --name-only && git ls-files --others --exclude-standard
```

### L2.2 总结本次开发

从对话上下文提炼：会话标题 / 改动文件 / 新增功能 / 修复改进 / 遗留问题。

### L2.3 待开发计划

遗留事项较多时，创建/更新 `plans/` 计划文档 + 更新任务队列。

### L2.4 记忆注入

有记忆采集脚本则跑（存在才跑，不凭旧记录断言工具可用性）。

### L2.5 写日志

journal 当日文件追加收工段；跨模块改动追加对应 DEVLOG。

### L2.6 更新 CHANGELOG

分类标记（`+`新功能 `↑`改进 `✓`修复 `↻`重构 `🔒`安全 `📝`文档 `⚙️`配置）追加到 CHANGELOG 顶部，不覆盖已有条目。

### L2.7 队列归档 + 关联文档

1. 扫描任务队列划线任务 → 追加到 CHANGELOG → 从队列删除；排队中第一个任务自动上位
2. 检查关联配置文档是否需更新；涉及文档层则做三层知识对齐（记忆层/agent 配置层/人类文档层）
3. 引用完整性自检（~30s）：对本会话新增/改写的引用路径 grep 相对路径存在性；重置/迁移/改名类结构性动作**必做**；断链先修再进 L2.8

### L2.8 Git 提交

按你工作区的提交权限口径执行（谁有权提交、提交前审查什么，遵循工作区规则）。生成 commit message（`<type>(<scope>): 简述`）+ 变更清单 → 提交。🔴 永不 force push（[Git 红线](../../rules/iron-rules.md) #20）。

### L2.9 展示总结

📊 变更统计 → 📝 日志预览 → ✅ commit 结果 → ⚠️ 遗留事项。收工时若当日已做过 L1.2 局外人审视，此处只引用其结论补差异，不重复全量审视。

## L3: 代码清洗（先审后洗）

### L3.1 质量快照

对目标项目执行（按语言换用对应工具链，示例为 Python）：

```bash
cd <project_dir> && ruff check src/ tests/ 2>&1
python -m pytest tests/ -q 2>&1
find src/ -name "*.py" | xargs wc -l | sort -rn | head -20
```

上帝文件（>300 行且内容密度低）标记为拆分候选。输出质量快照报告（模板见 [references/report-template.md](references/report-template.md)）。

### L3.2 ponytail 审查（过度工程，写码前后皆可）

> [溯源: DietrichGebert/ponytail 原创内化] 只针对过度工程和复杂度；正确性 bug/安全漏洞/性能不在此范围。

对 diff 或指定文件，每发现一个输出一行 `L<行号>: <标签> <发现> → <替换方案>`：

| 标签 | 含义 |
|------|------|
| `delete:` | 死代码、未使用的灵活性、投机特性 → 删掉 |
| `stdlib:` | 手写标准库已有的 → 标准库函数 |
| `native:` | 依赖做了平台已有的事 → 平台原生 |
| `yagni:` | 单实现抽象/没人设的配置/单调用者的层 → 内联 |
| `shrink:` | 同逻辑更少行 → 更短形式 |

评分 `net: -<N> lines possible`；无可删则 `Lean already. Ship.`。规则：自检测试/assert 从不标记删除；**只列出不应用修改**。结果写过度工程审查报告。

**阶梯检查（写码前，衔接 [极简沟通](../极简沟通/SKILL.md) 模式 C）**：这需要存在吗(YAGNI) → 代码库已有？ → 标准库有？ → 平台自带？ → 已装依赖能解决？ → 能一行？ → 最少代码。

### L3.3 渐进式清洗

1. 读取检查清单 [references/checklist.md](references/checklist.md)（工程原则勾选 + R1-R6 诊断四段式：🔴/🟡/🟢 + 症状/出处/后果/补救）
2. 读取拆分模式库 [references/patterns.md](references/patterns.md)
3. 分批执行：安全 → 上帝文件 → 防御式 → DRY → 可观测性+KISS；每批展示前后对比 → lint+测试验证 → 用户确认 → 生成 commit 草稿

## L4: 文档评审（F1-F2）

### L4.1 学习文档评审

准确性×3 + 完整性×2 + 实用性×2 + 可读性×1，满分 8 分。

### L4.2 Skill 安全审查

按你工作区的技能安全策略审查（无则按常识维度：网络请求/文件写入/凭据接触/破坏性操作/副作用范围）输出 ✅/⚠️/🔴；反馈循环最多 3 轮，🔴 必须修复。

---

## L5: 规范审查（轻量日常版）

> 定位：规范约束难完全避免跑偏，**日常就做轻量规范审查**，减少后续维护压力。全库全量的一致性扫描属重型清理，不在本技能。

### L5.1 一致性检查

对照当前改动的关联文件做局部一致性核对（命名/路径/版本号/引用），输出 ✅/⚠️/🔴 简报。

### L5.2 标记状态对齐

扫描本次涉及文件的前缀/状态标记（活跃/已完成等）与 TODO 注释，检查准确性；发现失准即列清单。

## 反借口表（Anti-Rationalization）

| 你正在想… | 实际情况 |
|-----------|---------|
| "这个改动太小了，不需要审查" | **小改动引入大 bug。** 系统稳定性取决于最弱的环节。 |
| "测试都通过了，没问题" | 测试只覆盖了你想到的 case。审查看的是你没想过的。 |
| "后面再修吧，先合并" | "后面再修"是良好意图的坟墓。**要么现在修，要么不会修。** |
| "这个 PR 已经很大了，再加几行没关系" | 大 PR 是审查盲点和合并冲突的磁铁。**拆开。** |
| "这是原型代码，不需要规范" | **70% 的原型代码最终进了生产环境。** 例外不是规则。 |
| "代码能跑就行" | **能跑的代码 ≠ 好代码。** 不规范的代码是技术债的源头。 |
| "这个抽象留着以后用" | 你在为还没到来的未来优化。**YAGNI。** 删掉它。 |
| "重构一下顺手就做了" | 重构和功能混在一起，两者都更难审查。**分开做。** |
