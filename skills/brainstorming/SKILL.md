# Skill: 头脑风暴 🧠

> 版本：1.2 | 安全等级：🟢 无风险（纯对话+文档）
> 灵感来源：obra/superpowers — brainstorming skill
> 链式衔接：头脑风暴 → 写计划 → 实现

---

## 目标

在任何代码编写之前，通过结构化对话将模糊想法精炼为清晰设计，产出设计文档并获得用户批准。

<HARD-GATE>
在用户批准设计之前，**绝不**写任何代码、创建任何项目、或执行任何实现动作。这适用于**每个**项目，无论看起来多简单。
</HARD-GATE>

---

## 反模式："这太简单了不需要设计"

每个项目都要走这个流程。一个 todo list、一个单函数工具、一个配置修改——全都需要。"简单"项目恰恰是未审视的假设造成最多浪费的地方。设计可以很短（真正简单的项目几句话就行），但你**必须**呈现设计并获得批准。

---

## 核心流程

### Checklist（必须按顺序执行）

- [ ] **1. 探索项目上下文** — 检查文件、文档、最近提交，了解现状
- [ ] **2. 一次一问** — 理解目的、约束、成功标准（每条消息只问一个问题）
- [ ] **3. 提出 2-3 种方案** — 附带权衡分析和你的推荐
- [ ] **4. 分段展示设计** — 按复杂度调整每段长度，每段后询问用户确认
- [ ] **5. 写设计文档** — 保存到 `plans/YYYY-MM-DD_<功能名>/design.md` 并 git commit
- [ ] **6. 设计自检** — 快速检查占位符、矛盾、歧义、范围
- [ ] **7. 用户审批设计** — 请用户审阅设计文档，等待确认
- [ ] **8. 转入计划编写** — 调用 [writing-plans](../writing-plans/SKILL.md)

### 流程图

```
探索上下文 → 一次一问 → 提出2-3方案 → 分段展示设计
    ↓                                        ↓
了解现状                              用户批准设计？
    ↓                                   ↙       ↘
一次一问                          修改设计    写设计文档
    ↓                                          ↓
理解目的/约束/成功标准                    设计自检
    ↓                                          ↓

    ↓                                   ↙       ↘
推荐最优方案                          修改文档    调用 写计划
```

## 具体指引

### 理解想法

- **先看项目现状**（文件、文档、最近提交），不要凭空提问
- **评估范围**：如果请求涉及多个独立子系统（如"构建一个包含聊天、文件存储、计费和分析的平台"），立即标记。先帮用户分解为子项目，然后逐个走设计流程
- **一次只问一个问题**——如果需要更多探索，拆成多个问题
- **尽量用选择题**，开放式也可以
- **聚焦理解**：目的、约束、成功标准

### 探索方案

- 提出 2-3 种不同方案，附带权衡
- 对话式呈现选项，给出推荐和理由
- **先说推荐，再解释为什么**

### 展示设计

- 分段呈现，每段复杂度匹配内容：简单内容几句话，复杂内容 200-300 字
- 每段后问"这部分看起来对吗？"
- 覆盖：架构、组件、数据流、错误处理、测试
- 随时准备回退澄清

### 设计隔离与清晰

- 将系统拆成更小的单元，每个有单一明确目的
- 对每个单元，你应该能回答：它做什么？怎么用？依赖什么？
- 不看内部能理解它做什么吗？改内部会破坏调用方吗？如果不能，边界需要优化

### 在现有代码库中工作

- 先探索现有结构，遵循已有模式
- 如果现有代码有问题（文件过大、边界不清），在设计中包含针对性改进
- 不要提议无关的重构

## 设计自检

写完设计文档后，以新视角检查：

1. **占位符扫描**：有没有"TBD"、"TODO"、未完成章节、模糊需求？有就修掉
2. **内部一致性**：各章节是否互相矛盾？架构是否匹配功能描述？
3. **范围检查**：这是否聚焦到可以用一个实现计划覆盖？还是需要分解？
4. **歧义检查**：任何需求是否可以有两种理解？如果是，选定一个并明确说明
5. **不确定性标记**：设计中是否有未标记的模糊处？→ 全部补标 `[NEEDS CLARIFICATION: 具体问题]` 或明确解决

发现问题直接修复，不需要重新审阅——修完继续。

## 设计文档模板

```markdown
# <功能名> 设计文档

> 创建：YYYY-MM-DD | 状态：待审批

## 目标
一句话描述要构建什么。

## 背景
为什么要做这个？（问题/动机/约束）

## 方案选择
### 方案A（推荐）：<名称>
描述 + 优势 + 劣势

### 方案B：<名称>
描述 + 优势 + 劣势

### 选择理由
为什么推荐方案A

## 设计详情

### 架构
整体结构、关键组件、组件间关系

### 数据流
数据如何流转（输入→处理→输出）

### 错误处理
异常情况如何处理

### 测试策略
如何验证功能正确性

## 文件结构
预计创建/修改哪些文件，每个文件的职责

## 影响范围
- 修改的现有文件
- 新增的依赖
- 对其他功能的影响

## 开放问题（如有）
> 所有未解决事项必须使用 `[NEEDS CLARIFICATION: 具体问题]` 格式标记

- [NEEDS CLARIFICATION: 具体问题] — ...
```

## 约束

### 必须做
- 设计文档使用与用户沟通一致的工作语言撰写
- 每份设计文档必须包含「目标」「方案选择」「设计详情」
- 设计文档保存到 `plans/YYYY-MM-DD_<功能名>/design.md`
- 设计完成后 git commit
- 获得用户明确批准后才能进入实现阶段

### 不要做
- ❌ 在设计批准前写任何代码
- ❌ 用"太简单"为借口跳过设计
- ❌ 提出没有权衡分析的单一方案
- ❌ 在一次消息中问多个问题
- ❌ 设计文档使用模板占位符不填充

## Red Flags（自我合理化警告）

| 你在想… | 实际情况 |
|---------|---------|
| "这太简单了不需要设计" | 简单项目是假设出错最多发的地方 |
| "先看看代码再说" | 设计先于代码审查 |
| "先搭个项目框架" | 没有设计的框架是浪费 |
| "我知道用户要什么" | 你以为你知道 ≠ 你真的知道 |
| "这个改动不需要走流程" | 每个创造性改动都需要 |

## 验证

> 全部通过才算完成（可检验的结果，不是"原则性符合"）。

- [ ] 设计文档已保存且无 TBD/TODO/未填充占位符；`[NEEDS CLARIFICATION]` 全部解决或显式标记
- [ ] 至少给出 2 种方案，附权衡分析与推荐理由
- [ ] 用户已明确批准设计；批准前零代码产出（HARD-GATE 未破）

**On failure:** 回到对应步骤（方案探索/分段展示）重新执行，不带着未批准设计进入实现。
