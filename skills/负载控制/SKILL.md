# Skill: 负载控制 🚦

> 上下文水位管理**决策层 + 手段层**：每轮回复前自检水位，逼近阈值时按决策树卸载
> 合并自三个内部技能：负载控制（决策层）、调度（手段① 派发）、任务拆分（手段② 细分）

---

## 为什么

两个根因：

1. **运行时崩溃线**：长会话高上下文水位可能触发 agent 运行时崩溃（实测某桌面 agent 的内嵌 JS 运行时在 ~300k token / 内存 commit ~0.93GB 时段错误，三次复现）。根治靠换运行时，但主触发路径是"单会话高负荷"——工程手段能把它压下去。
2. **相对百分比失真**：`>70%` 这类阈值是为 200K 窗口设计的；跑 1M 窗口模型时 70% × 1M ≫ 300k 崩溃线，阈值永远不触发，运行时先崩。**所以水位判据必须用绝对 token，不用相对 %。**

## 水位阈值（示例值，按你的环境校准）

| 等级 | 条件（示例） | 动作 |
|------|------|------|
| 🔴 硬 | 绝对 token ≥ 崩溃线 × 0.8（示例 250k）或内存 commit ≥ 崩溃值 × 0.85 | 进入决策树（留余量） |
| 🟡 软 | 硬阈值的 60%-100%（示例 150k–250k） | 主动预防：优先细分任务 |

**判定优先级**：绝对 token > 内存 commit > 相对 %（% 只作参考，跨窗口尺寸必失真）。

## 决策树（每轮回复前自检）

```
1. 读水位（状态栏 token 数 + 内存 commit）
2. 命中硬阈值？
   否 → 正常干活（软阈值区可顺手细分）
   是 → 进入负载控制：
      a0. Think in Code（首选动作）：统计/抽取/比对类工作改写脚本，只回传摘要
      a.  当前大任务能在 ~30k token 内收尾？
          能 → 极简沟通压缩 + 快速收尾 + 落盘(步骤 b) + 收工换会话
          不能 → 切片续跑：
      b.  落盘：进度 + 水位快照 + 下一步 写入 journal/_handoff（结构用 templates/HANDOFF.md）
      c.  细分：剩余工作 → 带预算子任务（手段②）→ 入派发队列（手段①）
      d.  选手段：可并行/属编程 → ①转派；须本会话线性续 → ③落盘换会话；范围过大 → ④降级缩减
      e.  通知用户：当前水位 + 所选手段 + 续跑点，然后换会话
```

## Think in Code（水位告警后的首选动作）

水位命中后**先改动作，再谈卸载**——省 token 的首选是"原始数据根本不进上下文"：

- **做**：统计/抽取/比对/汇总类工作，写一次性脚本执行，只把**摘要结果**回传上下文；大输出落盘，上下文里只留路径+结论。
- **禁**：连续 Read 逐条读同一目录/同一日志、用逐条工具调用做机械汇总、把原始数据整段贴回上下文。
- **量化依据**：同类任务的上下文占用差两个数量级——47 次逐条 Read ≈ 700KB vs 1 次脚本执行回传摘要 ≈ 3.6KB。
- **不适用**：探索性任务需要人眼扫原始数据（看体例/比措辞/抽查质量）——此时改用 [极简沟通](../极简沟通/SKILL.md) 压缩 + 分段读。
- **与四手段的关系**：Think in Code 是"不产生负债"；四手段是"负债已产生后怎么卸"。顺序：先 a0 后 a–e。

[溯源: context-mode「Think in Code」——"stop treating the LLM as a data processor, treat it as a code generator"；仅吸收思想与量化口径，不引入其工具]

## 水位归因（告警后先归因，再选手段）

同样是 250k，来源不同则最优手段不同；**归错因的手段是无效卸载**：

1. **列来源**：按占用从大到小，列本会话最大的几类工具输出——逐条 Read 累积、历史大文件整体读入、长回复/长工具结果增量、搜索/网页正文堆积、工具输出溢出机制回填的摘要+路径。
2. **归因 → 手段映射**：

| 主要来源 | 首选手段 |
|----------|----------|
| 循环/批量 Read、原始数据整段入上下文 | **Think in Code**（脚本回摘要） |
| 子任务可并行 / 属编程 | **手段① 转派** |
| 历史大读入已压在上下文（负债已成） | **手段③ 落盘换会话** |
| 搜索/网页正文堆积 | [极简沟通](../极简沟通/SKILL.md) 压缩 + 收窄抓取口径 |

3. **再动手**：归因结论与所选手段一并报用户。

> 为什么必须先归因：历史大读入撑满时转派子任务救不了本会话（负债还在）；反过来，若来源是"每次都要重读一遍原始数据"（动作问题而非负债问题），换会话只会再犯一次。

## 手段①：文件式任务派发（dispatch 协议）

多窗口/多 agent 场景，用**文件移动**表达任务状态，零基础设施：

- **任务文件**：`dispatch/{YYYYMMDD}_{HHmm}_{slug}.md`，含 Metadata（创建者/时间/严重度/项目）、Task Description、Context（目标目录/相关文件）、Acceptance Criteria
- **状态 = 目录**：`active/`（待领）→ `in_progress/`（已领）→ `completed/` | `rejected/`；状态流转只靠 `mv`
- **审计链**：每次流转在文件末尾「审计日志」区追加一行（时间 + 窗口/模型 + 动作 + 备注），只追加不改写——completed 文件应有 created → claimed → completed 三行审计，缺失即 ⚠️
- **三角色**：
  - **创建**（非编程/主窗口）：填模板入 `active/`，通知用户"已创建调度任务，请开一个合适窗口处理"
  - **领取**（编程窗口）：启动时 `ls active/`，用户选定后读文件、mv 到 `in_progress/`、按 Context 去目标目录工作；完成后追加 Result 区再 mv 到 `completed/`；无法完成则 mv 到 `rejected/` 并写明原因
  - **检查**（任意窗口）：遍历 `completed/`，读 Handoff 区，把结果消化进知识库/配置/记忆
- **完成定义**：Result 区必含 Work Summary / Verification / Handoff 三段

**批量任务先出清单再分发（规划门）**：fan-out 之前必须先产出「板块 × 任务 × token 预算」清单（每执行者一行：负责范围 / 任务 / 预计输入输出 / 预算 / 并发），**清单未出不得启动任何执行代理**；清单先向用户出示再分发，防口令变黑盒。

[溯源: oh-my-openagent「先规划再扇出应是机制强制而非 prompt 自觉」——只吸收口令→清单→分发的映射设计，不引入其运行时]

## 手段②：带预算任务细分

把粗任务切成**带 token 预算、可独立调度**的子任务：

1. **按产出边界切**（不是按时间）：每个子任务能**独立产出可验证结果**（一个文件/一个函数/一段研究）
2. **估预算**：读多少文件 × 大小 + 输出；**硬上限 ~50k/子任务**（≈ 硬水位的 1/5，留安全空间），超了继续拆
3. **三标注**：`Splittable`（能否再拆）/ `Parallelizable`（能否并行或可转派）/ `Dependencies`（前置子任务）
4. **入队**：按手段①模板建文件入 `dispatch/active/`，或挂任务队列

**Agent-Native 三原则**（子任务产物让 agent 能直接执行）[溯源: larksuite/cli]：
- **自包含**：含完整上下文（目标/相关文件/验收标准），领取后无需回问
- **可验证**：有明确完成信号（一个文件/一条测试通过/一段输出），agent 能自检
- **结构化字段**：用 Metadata/Task/Context/Acceptance 字段，不用自然语言段落

## 手段③：落盘 + 换会话

进度 + 水位快照 + 带预算的下一步写入 `_handoff`（结构用 [templates/HANDOFF.md](../../templates/HANDOFF.md)，<100 行）；新会话读交接文档续跑。适合须本会话线性继续的工作。

## 手段④：降级缩减

范围过大、预算不足以完整交付时：**缩减交付优先于死等**——与用户确认缩小范围（先交核心切片），不做半成品硬撑。

## 与其他技能的关系

## Red Flags

| 你在想… | 实际情况 |
|---------|---------|
| "水位到 70% 再处理" | % 判据跨窗口尺寸失真；用绝对 token |
| "逐条读完这些文件再说" | 循环 Read 是最大负债源；Think in Code 写脚本回摘要 |
| "换个会话就好了" | 动作问题（每次重读原始数据）换会话只会再犯；先归因 |
| "先分发 9 个子代理并行跑" | 无清单 fan-out 是翻车头名；先过规划门出清单，并发 ≤3 |
| "任务太大也得本会话扛完" | 预算不够就降级缩减，半成品硬撑是双输 |

## 验证

- [ ] 水位读数取**绝对 token**（非 %）；阈值已按本环境校准
- [ ] 告警后先 Think in Code、再归因，然后才选手段；归因结论已报用户
- [ ] 硬阈值触发时：落盘（_handoff 含水位快照 + 带预算下一步）+ 选手段 + 通知用户，三步全做
- [ ] 派发走文件协议（审计链完整，completed 三行不缺）；细分子任务 ≤~50k 且三标注齐全；批量分发前规划门清单已出示

**On failure:** 回决策树第 1 步重读水位；归因错了 → 回归因表重选手段。
